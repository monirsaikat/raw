Errors and logging

Every PHP warning becomes an exception, every uncaught exception becomes a proper response, and 5xx errors are written to a daily log file.

PHP errors

Bootstrap installs an error handler that throws ErrorException for warnings and notices, so a typo or an undefined key stops the request instead of printing into the page. The @ operator still silences a call. Deprecations are logged at notice level rather than thrown. Fatal errors are caught at shutdown and rendered like any other exception.

Stopping a request

abort(404);
abort(403, 'Members only');
abort(503, 'Down for maintenance', ['Retry-After' => '600']);
abort_if($order->paid, 409, 'Already paid');
abort_unless(auth_check(), 401);

These throw HttpException with a status, an optional message shown to the user, and optional headers. Other exception types the framework raises:

ExceptionStatusRaised by
HttpExceptionanyabort(), 404 and 405 from the router, 419 from CSRF, 429 from throttling
ValidationException422validated(); carries ->errors and ->input
AuthorizationException403authorize(), the can: middleware
QueryException500A failed SQL statement; message includes the SQL with bindings

How exceptions are rendered

  1. Any output buffered so far is discarded.
  2. A 5xx exception is logged with its stack trace.
  3. A ValidationException becomes a redirect back with errors and old flashed, or a 422 JSON payload for JSON clients.
  4. If the client wants JSON (Accept: application/json or a JSON body), the response is {"message": "..."}. In debug mode a 5xx payload also carries the exception class, file, line and trace.
  5. In debug mode a 5xx renders the debug page: the exception chain, a code excerpt around each frame's line, the stack trace without argument values (so credentials never reach the browser), request facts and the SQL log.
  6. Otherwise views/errors/{status}.tpl if it exists, else views/errors/error.tpl, with $status, $title and $message. Messages of non-HTTP exceptions are never shown outside debug mode.

The status line is sent explicitly, so non-standard codes such as 419 survive Apache.

Custom error pages

Create views/errors/404.tpl, views/errors/403.tpl, and so on. They are standalone templates (no layout) so they work even when the layout's data is unavailable; you can still {extends} the layout if you prefer.

Logging

log_info('User {id} logged in', ['id' => $user->id]);
log_warning('Slow import', ['rows' => $count, 'seconds' => $elapsed]);
log_error('Payment failed', ['order' => $order->id, 'exception' => $e]);
log_debug(...);   log_notice(...);   log_critical(...);   log_message('alert', ...);
log_exception($e);

Lines go to storage/logs/app-YYYY-MM-DD.log as [time] env.LEVEL: message {context as JSON}. Placeholders in braces are replaced from the context; the rest of the context is appended as JSON. LOG_LEVEL is the lowest level written (debug, info, notice, warning, error, critical, alert, emergency). If the directory is not writable the line falls back to PHP's error_log().

Query logging

With APP_DEBUG=true or DB_LOG_QUERIES=true every query is kept in memory for the debug page. DB_SLOW_QUERY_MS=200 writes a warning for anything slower. See Database.

Debugging helpers

dump($value, $other);      // pretty output (HTML in the browser, var_dump in the CLI)
dd($value);                // dump and stop
Post::where(...)->dd();    // the SQL with bindings substituted

Console and tests

In the CLI an uncaught exception prints its class, message and location (plus the trace in debug mode) and exits with status 1. The test runner catches exceptions per test and reports them as failures; the HTTP test client stores an action's exception on the response ($response->exception).
