Tooling

The developer tools around the framework: a debug toolbar on every page while developing, a generator that scaffolds a whole resource, an installer for new projects, a CI workflow, static analysis and versioning.

Debug toolbar

With APP_DEBUG=true every HTML page gets a collapsible panel fixed to the bottom of the window. The bar shows the response time (from the start of bootstrap), peak memory, the number of queries and their total time, the matched route, method, path and status, the logged-in user id, the number of included files and the number of log lines. Click it for the details:

  • Request: route path and name, action, the middleware chain, route parameters, PHP version.
  • Queries: every statement from Database::queryLog() with its bindings and time. Queries slower than DB_SLOW_QUERY_MS are highlighted.
  • Session: the keys in the session with truncated values. Anything named like a token, secret or password is shown as (hidden); the CSRF token never appears.
  • Logs: lines written with log_info() and friends during this request (an in-memory buffer kept by log_message() in debug mode).

The panel is injected before </body> by send_response(). Its CSS and JavaScript are inline and carry the request's CSP nonce, so the default Content-Security-Policy allows them. It is never added to JSON responses, redirects, error responses, non-HTML content types or bodies without a </body> tag, and the test client never sees it. When APP_DEBUG is off the cost is one boolean check per response.

SwitchEffect
APP_DEBUG=falseOff entirely (production).
APP_TOOLBAR=false / config('app.toolbar')Off while keeping the rest of debug mode.
?_toolbar=0Hidden for one request, e.g. to inspect the raw markup.
toolbar_disable()Hidden for the current request from inside an action (printable pages, HTML fragments).
toolbar_enable(true)Forces it on under the CLI so a test can assert on it; toolbar_collect($response) and toolbar_render($data) expose the pieces.

Scaffolding a resource: make:crud

php console.php make:crud Post --fields=title:string,body:text,published:boolean,summary:text?

One command writes everything a resource needs, in the same style as the hand-written code in the repository:

FileContents
models/Post.php$fillable from the fields and $casts for integers, booleans, floats and dates.
database/migrations/<stamp>_create_posts_table.phpSchema::create() with id(), one column per field (nullable() for ?) and timestamps().
database/factories/PostFactory.phpA fake() value per field.
policies/PostPolicy.phpAnyone may view; create, update and delete need a logged-in user. Add ownership checks once the table has an owner column.
controllers/PostsController.phpindex (paginated), show, create, store, edit, update, destroy; route model binding, authorize() against the policy, validated() with rules derived from the field types, flash messages.
views/posts/*.tplindex, show, create, edit and a shared _form, extending layouts/main.tpl with the Bootstrap markup used elsewhere, {csrf_field}, {method_field}, validation feedback and old input.
tests/PostsTest.phpListing, showing, guest access, creating, validation errors, updating and deleting through the HTTP test client on the in-memory database.

Field types: string, text, integer, boolean, float (decimal 10,2), date, datetime; int, bool and decimal are accepted aliases. Append ? for a nullable column with a nullable rule instead of required. Boolean fields become checkboxes; an unchecked box is stored as false.

Names follow the conventions of the rest of the framework: BlogPost gives the blog_posts table, BlogPostsController, views/blog_posts/, routes named blog_posts.index… and URLs under /blog-posts. Plurals use the simple rules of str_plural() (category → categories, box → boxes, post → posts).

The command prints the seven route lines to paste into routes/web.php; --routes appends them (once) as a commented block instead. Existing files are never overwritten unless --force is given, and a second run reuses the existing create_posts_table migration rather than adding another. Afterwards:

php console.php migrate
php console.php test posts

Installing a project

install.php in the project root prepares a fresh checkout. On an interactive terminal it asks for the application name, environment, database driver and credentials; in scripts and CI every answer is a flag and --no-interaction takes the defaults for the rest.

php install.php                                        # asks questions
php install.php --no-interaction --db=sqlite --migrate # scripted
php install.php --db=mysql --db-database=myapp --db-username=root --db-password=secret

It copies .env.example to .env (kept if it exists; --force rewrites it), writes the answers into it, creates the storage/ and bootstrap/cache directories and checks that they are writable, generates APP_KEY through console key:generate (skip with --skip-key), optionally runs the migrations (--migrate / --no-migrate) and prints the next steps.

create-project.sh starts a new application from a checkout of the framework: it exports the tracked files (git archive, or a plain copy without .git and runtime files) into a new directory, drops the benchmark folder, and runs install.php there with any extra arguments:

bash create-project.sh ../my-app --no-interaction --db=sqlite --migrate
cd ../my-app && php console.php serve

The repository also carries a composer.json with no dependencies (only the PHP version and extension requirements plus composer test, composer lint and composer analyse scripts) so the framework can be published and installed by name later. The framework's own autoloader is still the one in use.

Continuous integration

.github/workflows/tests.yml runs on every push and pull request with a matrix of PHP 8.2, 8.3 and 8.4 (shivammathur/setup-php with pdo_sqlite, mbstring, curl and openssl):

  1. php -l on every PHP file outside libs/.
  2. php install.php --no-interaction --db=sqlite to create the .env the bootstrap expects.
  3. php console.php test, the whole suite on the in-memory database.

A second job runs PHPStan on PHP 8.3. Both jobs must pass before a pull request can be merged if the branch is protected.

Static analysis with PHPStan

PHPStan is not a dependency of the framework; install it globally and run it from the project root:

composer global require phpstan/phpstan
phpstan analyse            # reads phpstan.neon

phpstan.neon analyses core/, controllers/, models/, policies/, helpers/, console/, console.php and install.php at level 6 and excludes libs/ and bootstrap/cache/. Because the framework is procedural, core/bootstrap.php is listed as a bootstrap file: running it registers the class autoloader and defines every function in core/*.php, the modules, helpers and middleware, so PHPStan can resolve them. console.php cannot be executed (it dispatches a command and exits), so it is listed under scanFiles for its command(), line() and write_stub() helpers; the Smarty sources are scanned for the View class. Missing iterable value types (array without array<string, mixed>) are ignored, which keeps the level useful for procedural code.

phpstan-baseline.neon records the findings in the existing code base so that the CI job is green and only new problems are reported. Fix some and regenerate it with phpstan analyse --generate-baseline; the goal is an empty baseline.

Versioning

The framework version lives in the VERSION file (currently 0.9.0) and follows Semantic Versioning: until 1.0, minor releases may change public helpers. CHANGELOG.md follows Keep a Changelog: an Unreleased section collects changes as they land, and a release moves them under a version heading with the date. Read it in code with file_get_contents(BASE_PATH . '/VERSION').
