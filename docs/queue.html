Queue

Push slow work (emails, exports, API calls) out of the request and run it in a background worker. Jobs are plain classes, the queue lives in your existing database, and the sync driver runs everything inline until you need a worker.

Why a queue

  • Faster responses. A welcome email or a PDF export takes hundreds of milliseconds the user does not need to wait for.
  • Retries. A job that throws is retried a configurable number of times with a backoff, then parked in failed_jobs where you can inspect and re-run it.
  • No new infrastructure. The database driver uses two tables in the database you already have. The sync driver needs nothing at all, so the same code works in development and in tests.

Defining jobs

A job extends Job and implements handle(). Scaffold one into jobs/ (autoloaded):

php console.php make:job SendWelcomeEmail
class SendWelcomeEmail extends Job
{
    public int $tries = 5;      // attempts before it is marked failed (default 3)
    public int $backoff = 60;   // seconds between attempts (default 0)

    public function __construct(public int $userId)
    {
    }

    public function handle(): void
    {
        $user = User::findOrFail($this->userId);
        // send the email...
    }

    public function failed(Throwable $e): void
    {
        log_error("Welcome email for user {$this->userId} gave up: " . $e->getMessage());
    }
}

Jobs are serialize()d when dispatched and rebuilt by the worker, so everything handle() needs must be a property. Store ids rather than whole models: the record is re-read when the job runs, which also means it sees the current state rather than a stale copy. Closures cannot be queued (PHP cannot serialize them); dispatch(fn () => ...) throws an explanatory exception.

Dispatching

dispatch(new SendWelcomeEmail($user->id));             // onto the default queue
dispatch((new SendWelcomeEmail($user->id))->onQueue('emails'));
dispatch_later(300, new SendWelcomeEmail($user->id));      // available in 5 minutes
dispatch_sync(new SendWelcomeEmail($user->id));            // run right now, ignore the driver

Queue::push($job);                 // same as dispatch(); returns the job id
Queue::later(300, $job);
Queue::push($job, 'database');     // a specific connection
Queue::size('emails');             // jobs waiting on a queue

onQueue() and delay() are fluent; the $queue and $delay properties can also be set as defaults on the class.

Drivers

Connections are defined in config/queue.php and picked with QUEUE_CONNECTION:

DriverWhat it doesUse for
sync (default)Runs handle() immediately inside dispatch(). Delays are ignored. A failing job calls failed() and rethrows.Development, small sites, tests that want the side effects.
databaseStores the job in the jobs table; queue:work picks it up. Reservation uses a transaction with SELECT ... FOR UPDATE plus a conditional update, so several workers can share the table.Production.
QUEUE_CONNECTION=database
QUEUE_NAME=default        # default queue name
QUEUE_RETRY_AFTER=90      # seconds before a reserved job is considered abandoned

The database driver needs the jobs and failed_jobs tables from the shipped migration: php console.php migrate. retry_after must be longer than your slowest job or a worker still running it will be handed a second copy.

The worker

php console.php queue:work                       # loop forever on the default queue
php console.php queue:work emails,default        # several queues, highest priority first
php console.php queue:work --once                # one job, then exit
php console.php queue:work --stop-when-empty     # drain the queue, then exit (cron)
php console.php queue:work --sleep=5 --max-jobs=500 --max-time=3600 --memory=256
  • --sleep: seconds to pause when the queue is empty (default 3).
  • --max-jobs, --max-time, --memory: exit after N jobs, S seconds, or once PHP uses that many MB. Code changes are only picked up by a fresh process, so let the worker exit periodically and have the supervisor restart it.
  • On Linux with ext-pcntl, SIGTERM lets the current job finish before the loop exits. Deploy scripts should send it and wait.

Each attempt is logged with log_info/log_warning/log_error, so storage/logs shows what ran and why something was retried. queue:listen is an alias of queue:work.

Supervising with systemd

# /etc/systemd/system/myapp-worker.service
[Unit]
Description=myapp queue worker
After=network.target mysql.service

[Service]
User=www-data
WorkingDirectory=/var/www/myapp
ExecStart=/usr/bin/php console.php queue:work --max-time=3600 --memory=256
Restart=always
RestartSec=3
KillSignal=SIGTERM
TimeoutStopSec=90

[Install]
WantedBy=multi-user.target
sudo systemctl enable --now myapp-worker
sudo systemctl restart myapp-worker   # after each deploy

Run a second instance (myapp-worker@1, @2 with a template unit) for more throughput; the database driver hands each job to exactly one of them.

Draining from cron

Where a long-running process is not possible (shared hosting), drain the queue every minute instead. Jobs wait up to a minute, which is fine for emails:

* * * * * cd /var/www/myapp && php console.php queue:work --stop-when-empty --max-time=55 >> storage/logs/worker.log 2>&1

On Windows use Task Scheduler with the same command, or run queue:work in a terminal during development.

Failed jobs

After the last attempt the job is moved to failed_jobs with its exception and stack trace, and its failed() method runs once. Manage them from the console:

php console.php queue:failed          # table of id, queue, job class, time, error
php console.php queue:retry 12        # push job 12 back onto its queue
php console.php queue:retry all
php console.php queue:forget 12       # delete one record
php console.php queue:flush           # delete all failed jobs (--jobs also clears pending ones)
php console.php queue:size emails     # jobs waiting

A payload whose class no longer exists goes straight to failed_jobs rather than being retried: renaming a job class while jobs are queued is the usual cause.

Testing with Queue::fake()

In tests, swap the driver for a recorder. Nothing runs or touches the database; you assert on what was pushed:

test('registering queues the welcome email', function () {
    Queue::fake();

    http_post('/register', ['name' => 'Ann', 'email' => 'ann@example.com', 'password' => 'secret123']);

    Queue::assertPushed(SendWelcomeEmail::class);
    Queue::assertPushed(SendWelcomeEmail::class, fn (SendWelcomeEmail $job, string $queue, int $delay) => $job->userId === 1);
    Queue::assertNotPushed(ExportReport::class);
    Queue::assertNothingPushed();          // fails here: one job was pushed
    Queue::pushed();                       // [['id', 'queue', 'delay', 'job' => Job], ...]
});

Call Queue::reset() in before_each to drop the fake and any memoised driver between tests. To exercise a job's real behaviour, use dispatch_sync() or leave the sync driver on, and to test the worker itself use use_test_database() and the database driver, as tests/QueueTest.php does.
