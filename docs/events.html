Events

A small dispatcher for decoupling side effects from the code that triggers them: event('user.registered', $user) runs every listener registered for that name, in priority order, and returns what they produced. Listeners are closures, class names resolved through the container, or global functions. Module: core/modules/10-events.php.

Firing events

Events are plain strings with dots for namespacing, or objects. A string event passes its extra arguments to each listener; an object event passes the object itself as the single argument and is named after its class.

$results = event('user.registered', $user, request_ip());   // every listener's return value, in order
$first = event_until('payment.gateway', $order);          // stops at the first non-null result

class OrderPaid { public function __construct(public Order $order) {} }
event(new OrderPaid($order));                              // listeners receive the OrderPaid instance

Listening

listen(event, listener, priority = 0) registers a listener. Higher priorities run first; equal priorities keep registration order. Patterns with * match several names ('user.*', or '*' for everything, handy for auditing).

listen('user.registered', fn (User $user) => log_info('Registered {email}', ['email' => $user->email]));
listen('user.*', 'AuditListener', 100);                     // AuditListener::handle(...$payload), built by the container
listen('order.paid', 'OrderNotifier@sendReceipt');          // a specific method
listen('cache.warm', 'warm_route_cache');                   // a global function

listeners('user.registered');   // resolved list, wildcards included
has_listeners('user.deleted');
forget_listeners('user.*');     // one pattern; forget_listeners() clears all

Registering listeners at boot

Application listeners live in listeners/ (autoloaded) and are wired up in config/events.php, which the module reads once during bootstrap. Scaffold a class with php console.php make:listener SendWelcomeMail --event=user.registered; event:list shows what is registered.

// config/events.php
return [
    'user.registered' => ['SendWelcomeMail', 'CreateDefaultSettings'],
    'user.*' => ['AuditListener'],
];

// listeners/SendWelcomeMail.php
class SendWelcomeMail
{
    public function handle(User $user): void
    {
        Mail::to($user->email)->send(new WelcomeMail($user->name));
    }
}

Constructor dependencies of a listener class are injected by the container, so a listener can type-hint a service the same way a controller does.

Queued listeners

When the queue module is installed, a listener class that implements the marker interface ShouldQueue, or declares public bool $shouldQueue = true;, is wrapped in a QueuedListenerJob and dispatched instead of running during the request. Without the queue module the same class runs inline, so app code does not change between the two setups.

class SendWelcomeMail implements ShouldQueue
{
    public function handle(User $user): void { /* runs on the worker */ }
}

Testing

Event::fake() disconnects the listeners and records every dispatch; Event::restore() puts the real dispatcher back. The assertion filters receive the payload arguments (the object for object events). Assertions throw a TestFailure inside the test runner.

test('registration fires user.registered', function () {
    Event::fake();

    http_post('/register', [...]);

    Event::assertDispatched('user.registered', fn (User $user) => $user->email === 'ann@example.com');
    Event::assertNotDispatched('user.deleted');
    Event::dispatched('user.*');           // [['event' => ..., 'payload' => [...]], ...]
    Event::assertNothingDispatched();      // after Event::fake() with nothing fired

    Event::restore();
});

Tests that register listeners of their own should call forget_listeners() in after_each(); the listener table is process-wide and is not reset between tests.
