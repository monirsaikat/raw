Security

What the framework does for you, what it expects from you, and the switches involved.

CSRF

The global csrf middleware rejects any POST, PUT, PATCH or DELETE request that lacks the session's token, answering 419. Forms include it with {csrf_field}; JavaScript reads it from {csrf_meta} and sends the X-CSRF-TOKEN header.

<form method="post" action="{navigate name='contact.store'}">
    {csrf_field}
    ...
</form>
fetch(url, { method: 'POST', headers: { 'X-CSRF-TOKEN': document.querySelector('meta[name=csrf-token]').content } })

To exempt a pure API, run it in its own entry point or replace the global list with global_middleware([]) and protect it with tokens instead. Cookies use SameSite=Lax as a second layer.

Response headers and CSP

config/security.php controls the headers sent on every response: X-Content-Type-Options, X-Frame-Options, Referrer-Policy, Permissions-Policy and a Content-Security-Policy that allows only same-origin scripts, styles, images and fonts. That is why Bootstrap is self-hosted. Inline scripts need the per-request nonce:

<script nonce="{csp_nonce}">...</script>

Edit the directives in the config to allow additional origins. HSTS_ENABLED=true sends Strict-Transport-Security on HTTPS responses; enable it only once the site is served exclusively over TLS, because browsers remember it for a year. X-Powered-By is removed.

Sessions and cookies

  • Session cookies are HttpOnly, SameSite=Lax, and Secure on HTTPS (or always, with SESSION_SECURE_COOKIE=true).
  • PHP strict mode is on, so a session ID chosen by the client is never accepted.
  • The ID is regenerated on login, logout and remember-me login, which prevents session fixation.
  • Idle sessions expire after SESSION_LIFETIME minutes.

Passwords and login

  • Passwords are hashed with password_hash() and re-hashed on login when the algorithm defaults change.
  • An unknown email is verified against a dummy hash so a login attempt takes the same time either way.
  • Login and registration are throttled per IP (throttle:5,1); adjust in routes/web.php.
  • Remember-me cookies hold a random token; only its HMAC (keyed with APP_KEY) is stored, so a leaked database cannot forge cookies. Logging out invalidates the token.

Input and output

  • input() and request() never include cookies, unlike $_REQUEST.
  • validated() returns only the fields you declared; mass assignment is limited further by each model's $fillable.
  • Smarty escapes every {$variable}; only |raw output is unescaped.
  • Redirects from back() and auth_intended() only follow same-host URLs (url_is_local()), closing open-redirect holes.
  • request_host() rejects header-injected values.

Database

  • Every value is bound; the raw helpers take bindings only.
  • Table and column names are validated against a strict pattern, so a user-supplied sort column cannot inject SQL. Operators and directions are whitelisted.
  • A failed connection is rethrown without the original exception, whose trace would contain the password.

Secrets and files

  • Secrets live in .env, which is git-ignored and blocked by .htaccess. .env.example holds placeholders.
  • The debug page never prints function arguments from stack traces.
  • Every directory except assets/ and docs/ denies web access through its own .htaccess.
  • Uploaded files should be moved outside the web root or into a directory that never executes PHP.

Authorization

Protect actions with policies and gates rather than ad-hoc checks, and put auth before can: in route middleware. A policy method is never called for a guest unless its first parameter is nullable. See Authorization.

Encryption and cookies

APP_KEY also drives an AES-256-GCM encrypter. A base64: key from key:generate is decoded to its 32 raw bytes; any other string is hashed with SHA-256 to a key. GCM authenticates the ciphertext, so a payload that was altered, truncated or produced with another key does not decrypt to garbage: it throws DecryptException.

$payload = encrypt(['user' => 5, 'plan' => 'pro']);   // base64(json{iv, value, tag}), safe in URLs, cookies, columns
decrypt($payload);                                    // ['user' => 5, 'plan' => 'pro'], DecryptException on tamper
encrypt_string('raw text');   decrypt_string($payload);   // strings without JSON encoding
encrypter();                                          // the Encrypter instance, keyed by config('app.key')

Cookies you set yourself go through the same encrypter, so the client can neither read the value nor change it:

cookie('theme', 'dark', 60 * 24 * 30);   // encrypted, HttpOnly, SameSite=Lax, Secure on HTTPS; 0 minutes = session cookie
cookie_get('theme');                     // 'dark', or null when missing, tampered or encrypted with another key
cookie('theme');                         // same as cookie_get()
cookie_has('theme');   cookie_forget('theme');
cookie('theme', 'dark', 0, ['samesite' => 'Strict', 'httponly' => false]);   // override attributes

Path, domain and the Secure flag follow config/session.php. Under the CLI (tests) nothing is sent; cookies_queued() lists what a request wrote as plain values, and cookie_get() reads back what the test set. The remember-me cookie keeps its own scheme: it holds a random token whose HMAC is stored in the database, which already makes it unforgeable without the key; encrypting it on top would only hide the user id and invalidate every existing cookie on upgrade.

Signed URLs

A signed URL carries a signature parameter (HMAC-SHA256 with APP_KEY over the full URL) proving the link was generated by the app and not edited. Use it for unsubscribe links, email verification, one-off downloads: anything reachable without a login. An expiry is part of the signed data.

get('/unsubscribe/{id:\d+}', 'NewsletterController@unsubscribe', 'unsubscribe', ['signed']);

signed_url('unsubscribe', ['id' => $user->id]);              // https://example.com/unsubscribe/5?signature=...
signed_url('unsubscribe', ['id' => $user->id], 3600);        // ...?expires=...&signature=... valid for an hour
signed_path('unsubscribe', ['id' => $user->id]);             // relative: /unsubscribe/5?signature=...
signed_url_valid();                                          // the current request; signed_url_valid($url) for any URL

The signed middleware answers 403 for a missing, altered or expired signature. The host is part of what is signed, so set APP_URL to the public address (scheme included) in production; without it the origin is derived from the request. Changing APP_KEY invalidates every link issued before.

HTTP caching middleware

Two opt-in middleware in core/modules/60-http-cache.php handle browser and shared caches for public GET pages. Directives use _ where HTTP uses - because commas separate middleware parameters:

get('/docs/{page}', 'DocsController@show', 'docs', ['cache.headers:public,max_age=3600,etag']);
get('/feed', 'FeedController@index', 'feed', ['cache.headers:public,max_age=300,last_modified=' . $time]);
get('/sitemap.xml', 'SitemapController@index', 'sitemap', ['cache.response:600']);
  • cache.headers sets Cache-Control from its directives (public, private, no_store, max_age=N, s_maxage=N, must_revalidate, immutable, ...). etag adds a strong ETag (SHA-1 of the body); last_modified=<timestamp> adds Last-Modified. When the request's If-None-Match matches (weak tags and lists included) or If-Modified-Since is not older than the resource, the response becomes an empty 304 that keeps only the validator and caching headers. Only 200 responses to GET/HEAD are touched.
  • cache.response:ttl stores the complete response (status, headers, body) in the file cache for ttl seconds, keyed by the full URL, and serves it with X-Cache: HIT and an Age header. It skips visitors who are logged in or have flash messages waiting, non-GET requests, non-200 responses and responses marked private or no-store, and it never starts a session for a client without a cookie. Pages that embed a CSRF token or per-user content should not use it. response_cache_forget($url) evicts one entry; cache:clear all.

security:check

php console.php security:check audits the deployment and exits 1 on any failure, so it fits in a deploy script:

$ php console.php security:check
Status  Check             Detail
------  ----------------  ---------------------------------------------
PASS    APP_KEY           32 bytes
FAIL    APP_DEBUG         true while APP_ENV=production
PASS    .env over HTTP    https://example.com/.env answered 403
PASS    storage/          writable
WARN    HSTS              APP_URL is https but HSTS_ENABLED=false
PASS    CSP               10 directives
FAIL    Database          root without a password on [mysql]

Checks: APP_KEY set with at least 32 bytes; APP_DEBUG off when APP_ENV=production; .env not served (an HTTP request to APP_URL/.env when APP_URL is set, else the dotfile block in .htaccess); storage/, storage/cache, storage/logs and bootstrap/cache writable; the Secure cookie flag and HSTS when APP_URL is https; a Content-Security-Policy; MySQL running as root without a password; and the session driver.

Checklist for production

  • APP_DEBUG=false, APP_ENV=production, a generated APP_KEY, then php console.php security:check.
  • HTTPS everywhere, then HSTS_ENABLED=true.
  • storage/ writable by the web server, everything else read-only.
  • Review config/security.php if you add third-party scripts or fonts.
  • Keep PHP and MariaDB updated; the framework has no other dependencies to track.
