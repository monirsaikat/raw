CComfreePHP docs

Performance

A request touches a few dozen small files and no framework object graph. ComfreePHP ships the tools to measure that on your own hardware, and every response reports how long it took.

Why it is fast

  • Small surface. Bootstrap loads about thirty files and registers a handful of closures. There is no service-provider phase, no event dispatcher warming up, no container scan.
  • Lazy everything. Sessions start on first use, the database connects on the first query, the template engine is created on the first render, the gate on the first check.
  • Pre-compiled routing. Static paths are an array lookup; dynamic paths use regexes compiled once and cached with route:cache.
  • No reflection on the hot path except the one call that builds the controller, and nothing is proxied.
  • OPcache-friendly. Plain files, no generated code at runtime, so the whole framework stays in the opcode cache.

Every response reports its time

Each response carries an X-Response-Time header measured from the start of bootstrap to the moment the body is sent. With APP_DEBUG=true the layout footer also prints Rendered in 5.4 ms · 2 MB · 1 query through the {perf_stats} template tag.

curl -sI http://localhost/myapp/ | grep X-Response-Time
X-Response-Time: 6.05ms

Measuring

In-process: console bench

php console.php bench times the framework's own pieces in one process: bootstrap, routing, query compilation, validation, collections, view rendering, whole requests through the test client, and database round-trips on SQLite and MySQL. Use --iterations=N to run longer and --json for machine-readable output. Run it with OPcache enabled for the CLI to match a web server:

php -d opcache.enable_cli=1 -d extension=pdo_sqlite console.php bench

End to end: console bench:http

php console.php bench:http <url> uses a built-in load client on PHP's curl extension (persistent connections, per-request timing with sub-millisecond resolution, no external tool) against a running server and summarises requests per second, latency percentiles and failures. Options: --requests=1000 --concurrency=10 --raw, and --ab to measure with ApacheBench (apache/bin/ab.exe in XAMPP, apache2-utils on Debian) instead of the built-in client.

php console.php bench:http http://localhost/myapp/ --requests=1000 --concurrency=10
php console.php bench:http http://localhost/myapp/api/ping --requests=1000 --concurrency=10

Comparing with other frameworks

The Comparison page publishes measured numbers against Laravel, Symfony and plain PHP on the same machine, and php console.php bench:compare name=url ... runs the same alternating-round ApacheBench comparison against any set of URLs. The benchmarks/ folder holds the equivalent routes and templates for the other frameworks plus a setup script, so anyone can reproduce the table on their own hardware.

What costs the most

  • Writing files on Windows. Real-time antivirus scanning re-scans every file whose content changed, which adds around 9 ms to a rate-limit counter update, a cache write or a session save. It is invisible on Linux and vanishes on Windows when storage/ is excluded from scanning. The bench command prints a reminder on Windows.
  • Sessions. Any page that renders the layout starts a session (CSRF token, current user). A JSON endpoint that touches none of that costs no session I/O.
  • Database round-trips. A MySQL query costs more than everything the framework does for a request combined. Eager load relationships, avoid N+1, and cache what does not change.
  • Template compilation. Compile checks are off in production; run view:clear after deploying templates rather than paying a filemtime() per template per request.

Production settings that matter

  • APP_DEBUG=false: no query log, no debug page, no template compile checks.
  • opcache.enable=1, and opcache.validate_timestamps=0 on immutable deployments. Check opcache_get_status()['cache_full'] once after deploying: a full cache silently recompiles files on every request, and the common 128 MB default fills up when several applications share one server.
  • php console.php route:cache after route changes.
  • Enable mod_deflate and mod_expires; the shipped .htaccess uses them when present, and asset() versions URLs so assets can be cached for a year.
  • Use simplePaginate() on very large tables to skip the COUNT query, and cursor() or chunk() for exports.
